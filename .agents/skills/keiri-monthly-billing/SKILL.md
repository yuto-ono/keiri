# 月次請求

CLI、承認境界、データ形式は [SPEC.md](../../../SPEC.md) の「CLI」「LLMへの委任」「月次請求Markdown」を参照する。送付報告や進捗確認だけの依頼では、その確認・記録に範囲を絞る。

## 資料の参照

keiriルートで `mise exec -- pnpm keiri …` を実行する。データの場所は、Node.jsの `--env-file=.env` で読み込んだ環境から `src/lib/server/data-directory.ts` の既存処理で解決する。

作業月の指定がなければ、既存の日付ユーティリティで `Asia/Tokyo` の今月を求める。作業月と各請求書の請求年月は区別する。

次の順で読む。

1. データディレクトリの `README.md`：請求対象の確認方法、完了条件などの共通ルール。
2. `monthly-billing/<年>/<2桁の月>.md`：既存の記録から再開し、なければ `status: pending` で作成する。
3. 取引先YAMLと `billingInstructions`：請求対象と請求条件。
4. 関連する既存請求書YAML：対象と請求書番号を照合し、重複作成を避ける。

資料の矛盾や不足は利用者へ確認し、条件が揃った対象は進める。過去の請求書は今回の条件の確認案を作る材料にできるが、利用者の確認なしに確定条件として扱わない。

## 利用者への確認

- 読み取った進捗と確認事項を取引先名ごとに整理する。回答済みの事項や完了した操作は引き継ぎ、残っている確認に絞る。
- 単価・請求日・支払期限はREADMEの方針に従い、参照資料から具体的な候補と根拠を示す。先月分がなく直近の別月を参考にする場合は、その旨を伝える。日付や単価を白紙の質問で利用者へ委ねない。
- 稼働時間など今回の入力が必要な事項は、候補条件と一緒に聞く。「この条件でよければ、稼働時間を教えてください」のように、条件の了承と不足情報の回答をまとめて返せる形にする。候補を作れない項目や資料の矛盾は明示して確認する。
- 発行に必要な内容が揃った保存済み下書きは、請求書番号・リビジョン・請求内容・合計を提示し、条件の確認と発行承認を一度に求める。稼働時間の回答や候補条件への了承だけを発行承認とは扱わない。

## 下書きと発行

- 下書きの作成・編集・検証は個別承認なしで行う。YAMLは直接読み、変更はCLI経由で行う。月次記録は直接編集できる。
- 作成成功後は請求書番号を月次記録の本文に残す。更新には、保存済みYAMLの全体と読み取ったリビジョンを使う。
- 金額計算と検証は既存のdomain処理とCLIを使う。引数や操作の詳細は仕様書または `mise exec -- pnpm keiri invoice --help` で確認する。
- 発行前に保存済みの請求書番号・リビジョン・請求内容・合計を提示し、明示的な承認を得る。下書き戻し・削除も対象と内容への承認が必要。
- 発行直前に再読込し、確認済みリビジョンと一致する場合だけ、その値を `invoice issue --revision` に渡す。変更されていれば内容を提示して再承認を得る。同じ対象とリビジョンへの承認は繰り返し求めない。
- 失敗時は成功扱いせず、再開に必要な未解決の問題だけを記録する。作成済みの下書きを自動削除・重複作成せず、競合時にリビジョンだけを差し替えて再実行しない。

## 記録と報告

月次記録は進捗を把握し、未完了なら再開するための最小限の記録にする。本文は自由記述を保ち、短い箇条書きや改行で読みやすくする。

- 取引先ごとの請求書番号・進捗、利用者の送付報告、請求対象の確認結果を簡潔に残す。
- 金額・明細・日付・口座・リビジョン・PDFパスなど、請求書YAMLで確認できる情報を転記しない。
- 承認・検証・コマンド実行の詳細や、解消済みエラーの経緯を操作ログとして残さない。
- 未完了事項は再開に必要な間だけ残し、解消時に取り除く。完了後に「残作業なし」の節や空の項目を残さない。

月次の進捗は請求書の状態から推測せず、READMEのルールに従う。

最後に、処理した請求書番号、発行したPDFのパス、確認待ちの事項と次の作業を簡潔に伝える。
